# ARQUITETURA OFICIAL DO PORTAL CDPNI
## Especificação técnica para evolução do projeto existente

### 1. Objetivo do projeto

Evoluir o Portal CDPNI para um portal institucional moderno, inspirado na organização visual de portais como UOL e Terra, mantendo uma interface própria, organizada, responsiva e fácil de administrar.

O portal deverá permitir que um administrador gerencie praticamente todo o conteúdo visual por meio do painel administrativo, sem precisar editar arquivos Python, HTML, CSS ou JavaScript para realizar alterações comuns.

O sistema deverá oferecer:

- Edição visual de textos.
- Cadastro e substituição de imagens.
- Publicação de notícias, comunicados e matérias.
- Banners e cartões clicáveis.
- Gerenciamento de links organizados verticalmente.
- Criação e organização de seções na página inicial.
- Pré-visualização antes da publicação.
- Layout com alinhamento consistente.
- Funcionamento em computadores, tablets e celulares.
- Preservação das funcionalidades já existentes.

### 2. Regra principal: preservar o projeto atual

O projeto já utiliza Python, Flask, SQLite, templates HTML, CSS, JavaScript e um painel administrativo.

Antes de alterar qualquer arquivo:

1. Analise a estrutura completa do projeto existente.
2. Identifique todas as rotas, páginas, tabelas, modelos, scripts e funcionalidades.
3. Determine quais arquivos são efetivamente utilizados.
4. Identifique duplicações, arquivos antigos e dependências.
5. Registre os recursos que precisam continuar funcionando.
6. Apresente a arquitetura proposta e a relação dos arquivos que serão modificados.
7. Aguarde aprovação antes de executar alterações estruturais.

Não reescreva o projeto inteiro sem necessidade. Não remova arquivos, tabelas, rotas ou funcionalidades sem comprovar que podem ser retirados com segurança.

Não substitua o banco de dados SQLite por outro sistema nesta etapa. Uma futura migração só deverá ser considerada se houver justificativa técnica concreta.

### 3. Arquitetura geral

Organizar o projeto em cinco camadas lógicas.

**Camada A — Interface pública**

Responsável pela apresentação do portal para os usuários.

Páginas previstas:

- Página inicial.
- Notícias e comunicados.
- Página individual de conteúdo.
- Páginas institucionais.
- Página de links e sistemas úteis.
- Páginas específicas de serviços.
- Página de pesquisa, se aplicável.
- Página de erro 404.
- Páginas adicionais criadas pelo administrador, quando implementadas.

**Camada B — Painel administrativo**

Responsável pela gestão do conteúdo e da aparência.

Módulos:

- Visão geral.
- Editor de conteúdo.
- Biblioteca de imagens e arquivos.
- Notícias e publicações.
- Banners e destaques.
- Gerenciador de links.
- Gerenciador de seções da página inicial.
- Categorias e menus.
- Páginas institucionais.
- Usuários e permissões.
- Configurações visuais.
- Histórico de alterações.
- Backup e restauração, integrados aos mecanismos existentes.

**Camada C — Lógica de negócio**

Separar as regras de funcionamento em módulos, sem concentrar tudo em um único arquivo.

Organização sugerida, a adaptar à estrutura encontrada:

- `auth`: autenticação, sessões e permissões.
- `content`: conteúdos, textos e publicações.
- `media`: imagens, documentos e biblioteca de arquivos.
- `banners`: banners e destaques.
- `links`: links e grupos de links.
- `pages`: páginas institucionais.
- `sections`: organização dos blocos da página inicial.
- `categories`: categorias e menus.
- `settings`: configurações do portal.
- `audit`: histórico de alterações.
- `database`: acesso e inicialização do banco de dados.

Esses nomes representam responsabilidades desejadas. Não crie arquivos vazios nem duplique funções existentes. A separação deverá ocorrer gradualmente, mantendo compatibilidade com as rotas atuais.

**Camada D — Persistência**

Utilizar inicialmente o SQLite existente.

O banco deverá armazenar os dados estruturados, como textos, títulos, URLs, categorias, posições, estados de publicação, configurações e referências aos arquivos.

Os arquivos de imagem e documentos devem permanecer em armazenamento de arquivos, com seus caminhos e metadados registrados no banco.

**Camada E — Interface visual e componentes reutilizáveis**

Criar uma base visual comum para o portal:

- Cabeçalho.
- Navegação principal.
- Contêiner de conteúdo.
- Colunas laterais.
- Cartões.
- Listas de links.
- Banners.
- Blocos de texto e imagem.
- Rodapé.
- Botões e formulários.
- Mensagens de sucesso e erro.

Os componentes deverão compartilhar padrões de largura, espaçamento, tipografia, bordas, cores e comportamento responsivo.

### 4. Editor visual de conteúdo

Implementar um editor visual de texto, preferencialmente baseado em uma biblioteca consolidada e compatível com o projeto.

O administrador deverá poder:

- Criar e editar títulos.
- Definir subtítulos e resumos.
- Editar o corpo do texto.
- Aplicar negrito, itálico, listas, títulos e links.
- Inserir imagens no corpo do conteúdo.
- Inserir links em palavras ou trechos.
- Definir legendas e textos alternativos.
- Visualizar o resultado antes de publicar.
- Salvar como rascunho.
- Publicar ou despublicar.
- Programar publicação, se tecnicamente viável na infraestrutura atual.

O conteúdo deve ser armazenado de forma estruturada e segura.

O HTML gerado pelo editor deverá ser sanitizado no servidor, permitindo somente elementos e atributos autorizados. Não confiar apenas na validação feita pelo navegador.

Não permitir que um texto inserido pelo administrador execute JavaScript arbitrário no portal.

### 5. Biblioteca de imagens e arquivos

Criar uma biblioteca de mídia integrada ao editor de conteúdo.

Funcionalidades:

- Enviar arquivos do computador.
- Mostrar miniaturas das imagens.
- Pesquisar arquivos por nome.
- Adicionar título, legenda, descrição e texto alternativo.
- Selecionar uma imagem já cadastrada.
- Reutilizar a mesma imagem em diferentes conteúdos.
- Substituir uma imagem sem precisar alterar manualmente os templates.
- Identificar imagens que estão em uso.
- Evitar exclusão acidental de arquivos utilizados.
- Validar extensão, tipo real, tamanho e conteúdo do arquivo.
- Gerar miniaturas e versões otimizadas, se apropriado.
- Preservar o arquivo original quando necessário.

Cada imagem deverá ter um identificador e metadados próprios.

Ao substituir uma imagem, definir claramente se a alteração afeta apenas um conteúdo ou todas as referências ao mesmo arquivo. O comportamento deverá ser explícito e confirmado pelo administrador quando houver risco de alteração global.

Não aceitar arquivos executáveis ou conteúdo ativo como se fossem imagens.

### 6. Modelo de conteúdo

Criar ou adaptar um modelo único de conteúdo reutilizável, evitando criar uma tabela diferente para cada tipo de publicação sem necessidade.

Campos conceituais:

- Identificador.
- Título.
- Subtítulo.
- Resumo.
- Corpo do conteúdo.
- Imagem de capa.
- Texto alternativo da capa.
- Legenda.
- Categoria.
- Autor.
- Data de criação.
- Data de atualização.
- Data de publicação.
- Estado: rascunho, publicado ou arquivado.
- Slug ou endereço amigável.
- Metadados para mecanismos de busca.
- Destino opcional de clique.
- Indicação de destaque.
- Ordem de exibição, quando aplicável.

O modelo definitivo deverá ser ajustado às tabelas e funcionalidades que já existem no projeto.

Não duplicar registros existentes nem executar migrações destrutivas.

### 7. Banners, cartões e conteúdo clicável

Permitir criar blocos de conteúdo com imagem, texto ou ambos.

Tipos previstos:

- Banner principal.
- Banner secundário.
- Cartão com imagem e título.
- Cartão com título e resumo.
- Destaque editorial.
- Link visual para sistema externo.
- Atalho para página interna.
- Galeria de imagens.
- Bloco de conteúdo institucional.

Cada bloco deverá permitir configurar:

- Título.
- Texto opcional.
- Imagem opcional.
- Texto alternativo.
- URL de destino.
- Destino interno ou externo.
- Comportamento de abertura.
- Estado ativo ou inativo.
- Ordem de exibição.
- Localização no portal.
- Período de exibição, quando necessário.

Quando o bloco for clicável, definir uma área de clique clara e acessível. Não criar elementos interativos aninhados que causem conflitos, por exemplo, um link dentro de outro link.

### 8. Gerenciador de links verticais

Criar um módulo completo para administrar grupos de links, com cada link em uma linha separada.

O administrador poderá:

- Criar, editar, ordenar, ativar e desativar links.
- Definir nome, URL, descrição e ícone.
- Criar grupos com títulos próprios.
- Alterar a ordem dos grupos e dos links.
- Selecionar onde cada grupo será exibido.
- Reutilizar grupos em diferentes páginas.
- Definir se o destino abre na mesma aba ou em uma nova.
- Visualizar a lista antes de publicar.

Localizações possíveis:

- Coluna lateral esquerda.
- Coluna lateral direita.
- Página inicial.
- Rodapé.
- Página institucional específica.
- Página dedicada a links e sistemas.

Cada grupo deverá ter:

- Identificador.
- Título.
- Descrição opcional.
- Localização.
- Página vinculada, quando aplicável.
- Ordem.
- Estado ativo ou inativo.

Cada link deverá ter:

- Identificador.
- Grupo associado.
- Nome.
- URL.
- Descrição opcional.
- Ícone opcional.
- Ordem.
- Estado ativo ou inativo.
- Comportamento de abertura.

Validar URLs no servidor. Permitir somente esquemas autorizados, como `https`, `http` e caminhos internos válidos. Bloquear esquemas perigosos como `javascript:` e `data:` para navegação.

A interface pública deverá mostrar listas organizadas, legíveis e com espaçamento consistente.

### 9. Gerenciador de seções da página inicial

Criar um sistema para configurar a ordem e a visibilidade dos blocos da página inicial sem editar os templates manualmente.

O administrador deverá poder:

- Adicionar seções disponíveis.
- Escolher o tipo de seção.
- Definir título e subtítulo.
- Selecionar os conteúdos apresentados.
- Definir quantos itens serão exibidos.
- Alterar a ordem das seções.
- Ocultar e reativar seções.
- Escolher a localização, dentro das opções suportadas.
- Visualizar a página antes da publicação.

Tipos de seção possíveis:

- Últimas publicações.
- Destaques.
- Notícias por categoria.
- Banners.
- Links úteis.
- Sistemas internos.
- Comunicados.
- Galeria de imagens.
- Bloco de texto institucional.
- Conteúdo selecionado manualmente.

A ordem, a visibilidade e os conteúdos selecionados deverão ser persistidos no banco de dados.

Não permitir que a configuração do administrador injete código executável ou HTML arbitrário.

### 10. Sistema de alinhamento visual

Esta etapa é obrigatória antes da ampliação das funcionalidades visuais.

Definir uma grade central de referência, com larguras, espaçamentos e pontos de quebra padronizados.

Estabelecer:

- Largura máxima do conteúdo.
- Margens laterais consistentes.
- Espaçamento vertical uniforme.
- Espaçamento horizontal
